What I learned wiring an MCP server to Supabase

A weekend spent connecting Claude to a live build-for-rent deal database via the Model Context Protocol. Tool design, auth, and the moment it started catching things I’d missed in the underwriting memo.

By Herman Chan Filed under AI Tooling

For the last year, the most useful thing I do at work is move data between a spreadsheet and a person. A broker emails a deck, I extract the unit mix into our model, run the comps, write a one-page memo, send it back upstream. The model is the same every time. The work is the joining.

So I spent a Saturday in May wiring our underwriting database into Claude through a Model Context Protocol server, mostly to see whether the joining would still feel like work afterward. Short answer: less of it does, and the parts that remain are the parts I actually wanted to be doing.

This post is a working log, not a tutorial. I’m going to skip the “what is MCP” preamble — Anthropic’s docs cover it better than I will — and write about the five decisions that mattered, in the order they came up.

§ 01The setup

The database is a Supabase Postgres instance with about forty tables. Three of them matter for underwriting: deals, comps, and permits. The rest are operational furniture — user accounts, audit logs, attachments. I wanted Claude to see the first three. I wanted it to not see the rest, ever, by construction rather than by trust.

My constraint was: a teammate should be able to install the MCP server locally, point Claude Desktop at it, and start asking questions about deals they have permission to see — without me handing them an API key or running anything on their behalf.

file · server.py python 3.12 
# the smallest thing that worked end-to-end
from mcp.server.fastmcp import FastMCP
from haven.db import session_for_user

app = FastMCP("haven-deals")

@app.tool()
def get_deal(deal_id: str, *, user: str) -> dict:
    """Fetch a single deal with unit mix, rents, and the latest comp set."""
    with session_for_user(user) as s:
        return s.deals.get(deal_id).as_context()

if __name__ == "__main__":
    app.run()

That “session_for_user” line is doing all the work of the auth section below. We’ll come back to it.

§ 02What MCP actually gives you

The Model Context Protocol is a small contract: a server exposes tools (callable functions), resources (readable documents), and prompts (templated starting points). The client — in my case Claude Desktop — calls them on the user’s behalf, surfaces the results, and lets the model reason over them.

The thing the docs don’t emphasize enough: your tool definitions are the prompt. Their names, parameter shapes, and docstrings are what the model uses to decide what to call. If you ship a tool called query_database(sql), you are functionally giving the model a SQL REPL and a vague nudge. If you ship find_comps_within(zip, radius_mi, bed_count) you have done most of the design work.

The schema you expose to the model is the schema of the conversation. The model will not be more careful than your function signatures invite it to be. — working note, sat afternoon

§ 03Auth without a service in the middle

The auth model I landed on is unglamorous: the MCP server reads a user’s short-lived Supabase JWT from ~/.haven/credentials, refreshes it lazily, and uses it to open a connection that inherits row-level security from Postgres. No service role keys, no proxy, no “trust the LLM not to mention table X.”

What this buys me:

  • Tool calls run as the user, not as the server.
  • The model literally cannot read deals the user can’t see — RLS rejects the query.
  • An audit trail lands in our existing logs, unchanged, alongside the queries a human would have run by hand.

The cost is one piece of installation friction: a teammate runs haven login once. That seems fair.

§ 04Designing the five tools

I ended up with a deliberately small surface. Each tool was named for the question a human would ask, not the table it reads from.

compare_to_buyboxdeals, buyboxPass/fail per criterion61

The last one is the only tool that writes anything. It writes a draft into a scratch table tied to the user, never into the canonical deal record. Reversibility is the cheapest form of safety.

§ 05The moment it caught something

On the second day, I asked Claude to underwrite a 184-unit BFR community outside Tucson that I’d already memo’d the previous week. I wanted to see if it would arrive at a number near mine.

It did — within 30 basis points on yield-on-cost. But then, unprompted, it noted that two of the three permit comparables I’d cited had been amended in March to a lower density, which would tighten our per-unit basis assumption by about $3,400. I’d read those permits in February. I hadn’t re-checked them.

Was the model being clever? Not really. It called recent_permits, saw the amendment dates, and noticed they were after the date in my memo footer. A junior analyst with the same instructions would have caught the same thing. The point isn’t that the model is smart; it’s that the joining cost dropped to zero.

§ 06What I’m doing next

Three things, in order:

  1. Adding a flag_for_human tool so the model has somewhere to put things it isn’t sure about — instead of guessing or quietly omitting them.
  2. Logging every tool call through llm_obs so I can see, after a month, which tools are pulling weight and which are dead code.
  3. Writing the “how to install this if you’re on our team” doc, which is going to be the difference between a weekend experiment and a thing two other people use.

If you’re building something similar — particularly the auth-pass-through piece — I’d love to compare notes. Email’s on the homepage.
